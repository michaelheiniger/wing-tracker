# 33. The logbook is synchronised between devices through a Git repository

Date: 2026-10-23

## Status

Accepted

## Context

Pilots keep one logbook on several devices and want it synchronised, attachments included. A synchronised folder (ADR 0020) copies files but resolves a conflict by keeping a stray copy nobody notices, and keeps no history. A database with a sync service (SQLite with PowerSync or Supabase) is the most user-friendly way, but it is a new storage backend and a hosted service. The JSON layout of one file per aggregate (ADR 0010) already suits Git: changes to different aggregates never collide, and every clone is a full copy. Users are technical pilots for now; a friendlier solution may replace this one later. Alternatives considered for the details: Git LFS for attachments (partial JGit support, host quotas), attachments in S3 (two channels to keep consistent), SSH keys (extra library, platform-specific agents), the `git` command (not installed on most Windows machines), committing from wrappers around the repository ports (they see single saves, not a use case's whole change), automatic conflict resolution by newest change (loses edits silently, depends on device clocks) and field-by-field merges (merge rules per aggregate).

## Decision

- **Port.** The application layer defines a `LogbookSync` port and the sync use cases in a new `sync` package. It speaks of pulling, pushing, status and conflicts per aggregate, never of Git, so another adapter can replace this one. Failures are typed (no connection, token refused, no such repository, remote not a logbook, unexpected) so only composables turn them into text (ADR 0014).
- **Adapter.** A new JVM-only module, `infrastructure-git`, implements the port with JGit (version in the version catalog). The data folder is the working tree. Files are committed byte for byte, without line-ending conversion. The storage adapter, wired in the composition root, tells it which aggregate a file belongs to and which files are quarantined; it knows nothing else of the layout.
- **What is synchronised.** Every aggregate and every attachment (ADR 0011) in plain Git: attachments never change once stored, so each is kept once. The settings are split into logbook settings (synchronised, e.g. reminder lead times) and device settings (not synchronised, e.g. the last backup, cloud backup settings); both stay in the data folder. The quarantine folder (ADR 0015) and temporary files are ignored, and a record moved to quarantine is never pushed as deleted.
- **Commits.** Each use case that changes the logbook runs its writes in a transaction of the `LogbookTransactions` port, described by a typed `LogbookChange`. The transaction travels in the coroutine context, so repository signatures do not change, and a use case called inside another joins the outer transaction. Each transaction becomes one local commit of the files it changed, attachments included and the quarantine left out; committing never touches the network. The commit message is written in English by the adapter from the `LogbookChange`: it is read in the Git history, not shown in the app (ADR 0014). A pull or push waits for a running transaction to finish, so it never sees half a change. Without sync, a transaction only runs its block.
- **No rollback yet.** A transaction that fails or is cancelled leaves the files as the use case wrote them, and the compensations of ADR 0011 stay. What it wrote is committed all the same, under its change marked as interrupted, so the history matches the disk and the next transaction is not blamed for it. The port is shaped for a transactional storage adapter that stages writes and applies them at once; that adapter would need its own ADR, as it changes how writes are made atomic (ADR 0010).
- **When.** Synchronising runs in the foreground only (ADR 0012): before the repositories load at start, with a "Skip" and continuing offline without a connection; when the app closes, with a "Close without syncing" and closing anyway on failure; and on demand. Local commits not yet pushed are pushed at the next sync.
- **Conflicts.** Changes to different aggregates are merged. When both sides changed the same aggregate (including one side deleting it), the local version stays on disk, the pilot is shown both and chooses, and nothing is pushed until every conflict is resolved. Closing never waits for a resolution; conflicts found then are shown at the next start.
- **Backups.** The repository is part of the data folder, so a backup (ADR 0031) carries it with its history and the device settings, and a restored backup is still connected to its remote. A backup waits for a running transaction or sync to finish, like a pull does.
- **Authentication.** HTTPS with a personal access token the pilot pastes once, kept by the OS through the `CredentialStore` port (ADR 0029). The remote's address is a device setting.
- **Connecting.** A logbook with data is connected to an empty remote by committing everything and pushing. A device without data is connected to a remote holding a logbook by cloning into a free folder that becomes the data folder through the change-and-restart flow of ADR 0020. Connecting a logbook with data to a remote holding another logbook is refused; merging two logbooks is a feature of its own.

## Consequences

The logbook is on every device and offline in between, each change is in a history that a later view or undo can use, and any Git host works, without a server of our own. Nothing is ever removed from the history: deleted flights and attachments stay in it and the repository only grows, and anyone with access to the repository can read the whole logbook. Every use case that writes must declare its transaction; one that forgets leaves its change uncommitted until the next transaction picks it up under the wrong description. Settings are split, which changes the settings schema and the content of a backup (ADR 0031). Backups grow with the history. Restoring an older backup on a synchronised device does not bring the logbook back to that state: the next pull brings it forward to the remote again, so going back is done in the history instead. Devices on different versions can work together because a record written by a newer version is left in place (ADR 0015), but they cannot edit it. Creating a token and a repository is left to the pilot, which is acceptable for technical pilots only. Mobile and web need another JGit-free adapter or another `LogbookSync` implementation.

## Amendments

- 2026-10-24: A transaction that fails or is cancelled is committed with what it wrote, marked as interrupted, instead of committing nothing. Without rollback, a batch cancelled halfway (an air-time export, a Syride import) leaves real changes on disk; committing nothing would have let the next transaction claim them under its own description.
- 2026-10-24: Details settled while building it. Signing in takes an optional username next to the token, since some hosts need one. Commits carry the name and email address the pilot gives when connecting, kept in the device settings. A sync rebases this device's commits onto the other devices' ones, so the history stays a straight line; any file changed on both sides since the last sync is a conflict, even when Git could merge its lines. Changes made outside the app (edited by hand, moved back from quarantine) are committed before a sync. Until the pilot can choose between versions, a sync with conflicts exchanges nothing and names the records. A backup waits for a running transaction or sync through the `LogbookTransactions` port.
